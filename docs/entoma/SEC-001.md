Scope: secure journal persistence and its session/UI gates; no financial request,

**Formal Security Delta Re-review REQUIRED / PENDING. Do not merge automatically.**

## Problem and change

Pinned `flutter_secure_storage` 10.0.0 Android Dart options enabled reset on error.
Native `read()` can delete an unreadable key and retry, returning null. The outer
plugin error fallback can delete all items and return a reset marker. Automatic
algorithm migration also performs multiple writes/key changes, not an atomic journal
transaction. Neither response establishes an empty operation history.

NativeSessionVault now explicitly retains the pinned RSA-OAEP/AES-GCM algorithms,
namespace and keys, disables `resetOnError` and `migrateOnAlgorithmChange`, and still
uses the existing native keychain/Keystore. No deleteAll or automatic risk reset exists.

The live provider uses IntegritySessionVault with an independent, origin-scoped,
non-secret preferences witness. It holds only schema/state/digest; secure v2 journal
holds all accounts' pending keys. Android's pinned legacy preferences setter uses
synchronous `commit()`, checks its result and reloads. Every replacement validates
the previous digest, persists dirty witness, writes and verifies the secure journal,
then completes the witness. A dirty checkpoint is not automatically rolled back.
Missing/invalid/mismatched records, failed writes and stale candidate digests fail closed.
Instances sharing a witness serialize in-process; desktop already has a single-instance
lock. This does not implement a cross-device or adversarial multi-process transaction.

Legacy complete journals are strictly parsed and migrated without discarding other
accounts or unknown records. Legacy login always wrote a journal, so an existing
session with no journal is quarantined. v2 journal with no witness also quarantines.
Normal preference reset preserves all integrity witness keys.

Journal trust is independent of account-token availability. Intact session storage
allows login, account/subscription/order/ticket GETs and cached proxy use. Untrusted
journal blocks every session-dependent non-idempotent request, mutation, recovery
retry and new-intent acknowledgement. Terminal GET DTOs remain viewable but do not
clear quarantined records. Login/logout cannot overwrite a damaged journal; logout
still attempts token removal and owned-profile cleanup. A separate warning directs
the user to support and explicitly states that re-login does not remove protection.

## Remaining boundaries

Deleting ALL secure records and witness is indistinguishable from fresh install.
Rolling both back to the same matching old checkpoint cannot be detected locally.
Android backup is disabled, but local integrity is not a server operation ledger.
Reinstall/clear-data, compromised same-user/root state, multiple devices and requests
sent before a client crash ultimately need server-side idempotency/operation receipts
and an authoritative reconciliation contract in Solution/V2Board. No backend change
is authorized or included here. A single terminal order GET cannot prove that every
lost unknown operation across accounts is resolved; support alone does not unlock it.

Disabling migration may reject an existing store using different algorithms rather
than erase it. Such a migration requires separate controlled verification. If native
session storage itself is unreadable/unwritable, authenticated reads/login cannot be
promised; local interface and cached proxy remain available where core preparation
succeeds. No general client security or production release acceptance is claimed.
