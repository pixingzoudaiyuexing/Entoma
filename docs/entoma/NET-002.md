# ENTOMA-NET-002: Android true exit

Base: `83214dd041f5f377d6577319cd290b9bc3a2c67c`.

Huawei CDY-AN90 / Android 10 previously left the VPN/TUN alive when Android
Back performed true exit with `minimizeOnExit=false`. The old controller closed
listeners and destroyed the service engine without stopping the VPN; a 300 ms
exit timer and unconditional final Activity pop raced all cleanup.

Android now owns a single-flight exit transaction: close native start admission,
drain retained service startup and admitted configuration work, save preferences,
await native VPN stop, await core shutdown, destroy the service engine, then finish
the Activity. False results and errors do not permit an early Activity exit.
Once core teardown has been dispatched, an unknown result keeps start admission
closed until an explicit exit retry reconciles it. Minimizing follows the existing
background path and does not enter this transaction.

Native stop invalidates pending permission and Binder generations, awaits
`Core.stopTun`, checks the recorded TUN descriptor, stops foreground service
state, unbinds and waits for observed services' `onDestroy` acknowledgements.
The caller's 15-second deadline does not cancel or forget an in-flight native
cleanup; retry joins it and engine destruction remains blocked. Readback never
closes a numeric FD itself or changes JNI/Go ownership.

Retaining an active background engine also requires reconnecting a recreated UI
to its private isolate ports. Quick startup registers the same port binding and
owns a readiness barrier. Replies remain bound to the submitting UI; ordinary
node delay and status requests retain their existing concurrency.

## Validation and review boundaries

- Flutter coordinator and actual-controller tests cover slow stop beyond 300 ms,
  failure/false results, duplicate exits, preference write failure, admitted work,
  new-start rejection, Activity order and minimization.
- Kotlin tests exercise the production lifecycle guard, stop transaction and
  service registry: late tokens, duplicate stops, failure/retry, timeout ownership,
  late service creation and delayed success delivery.
- Real ReceivePort tests cover old/new UI reply ownership, readiness and request
  concurrency; mutation checks prove these tests reject broken behavior.
- The artifact workflow runs the Android Kotlin tests in addition to Flutter/Go.
- Physical Huawei results, APK/source identity, exact CI and remaining unknowns
  are recorded in the delivery evidence; build/unit success is not device proof.

The registry covers observed service identities. Exact framework delivery of an
already-requested but not-yet-created bound service remains a device-validation
boundary; a main-loop yield alone is not a universal AMS barrier. FD readback is
conservative and non-atomic; it may reject an ambiguous reused TUN identity.

H02 remains SYNTHETIC ONLY and is not repaired here. The mihomo pin, default mixed
stack, credentials, payment Journal and subscription behavior are unchanged.
No account data is cleared for testing. Formal Independent Delta Review is
REQUIRED before merge; this document and internal checks do not satisfy that gate.
